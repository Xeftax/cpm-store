1 · Where the council agrees (validé, haute confiance)

D2 — Apache-2.0

Validé par les 5 sans réserve. Compatible GPLv3/AGPL de linphone-sdk.

D4 — workspace crates/*, MSRV 1.85, édition 2024

Validé, avec une condition : la CI linphone-sdk (vieux builders NDK) doit accepter Rust 1.85.

D6 — JSON only

Validé : le SCR rend le JSON Mandatory, le XML Optional.

D5 — FFI C (cbindgen)

Tient, mais le contrat FFI s'écrit avant la phase 6 : tokio global (OnceLock), vtable C explicite, catch_unwind à la frontière.

D3 — direction

L'état de synchro (restartToken/lastModSeq) entre dans le contrat : SyncState sérialisable stocké par l'hôte ; les traits portent les messages.

Specs

REST_NetAPI_NMS embarquée + QA'ée avant la phase 2 (fait le 2026-11-08) ; annexes B/C–H extraites du PDF (pdftotext) pour les golden tests.

Publication

Aucun dérivé OMA publié avant vérification des droits de redistribution.

3 · Blind spots (ce que seule la peer review a vu)

Juridique : Apache-2.0 ↔ AGPLv3 au linkage

0/5 conseillers3/5 reviews
Personne n'a analysé D2 face au host GPLv3/AGPL : combined work, clause brevet, §13 AGPL (obligations de source), versioning de l'ABI C. Action : faire valider par un juriste avant toute intégration linphone-sdk.

Chiffrement du backup (E2E, garde des clés, GDPR serveur)

0/5 conseillers2/5 reviews
Backuper des conversations expose le contenu : E2E, custodia des clés, effacement côté serveur. Action : documenter hors périmètre V1, à traiter avant toute mise en prod.

Contraintes mobile réelles

1/5 conseillers2/5 reviews
Taille binaire, mémoire, batterie ; CI NDK (vieux builders) vs MSRV 1.85 / édition 2024. Action : check CI linphone-sdk en phase 6.

Conflits multi-appareils + migration des historiques

0/5 conseillers1/5 reviews
Sémantique de conflits et migration des conversations Linphone existantes : absentes des 5 réponses. Action : scope phase 4 (sync).

Risque produit : client sans serveur

1/5 conseillers2/5 reviews
Sans serveur NMS déployé derrière, la lib reste un client orphelin. Action : nommer la cible d'interop + qui pilote l'intégration Linphone.

4 · Verdict du chairman

The Recommendation

  • Valider D2, D4, D6 telles quelles.
  • D5 validé à condition d'écrire le contrat FFI avant la phase 6.
  • D3 re-scopé : traits = messages + SyncState sérialisable stocké par l'hôte (1 clé), mapping objectId↔message dans cpm-core dès la phase 1.
  • D1 validé sous condition suspensive : REST d'abord tient si REST_NetAPI_NMS embarquée+QA'ée avec cible d'interop nommée avant la phase 2 — sinon on inverse et l'IMAP devient le plan A.
  • Publication publique bloquée jusqu'aux vérifications droits OMA + juridique AGPL.
  • Golden tests annexes C–H exclusivement depuis le PDF.

The One Thing to Do First

Embarquer REST_NetAPI_NMS dans le dépôt avec le même pipeline QA que les autres specs — 4/5 conseillers convergent là-dessus. Fait le 2026-11-08 (PDF officiel + conversion docling + QA 12/12 clés, voir docs/specs/README.md). Prochaine étape : nommer la cible d'interop réelle.
